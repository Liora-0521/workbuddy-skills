概念学习指南

大模型的上下文

上下文是模型单次推理时能看到的全部输入。它既是模型唯一的"工作台"，也是它最贵的资源——能放进去，不等于能用上。

本文范围：只讨论推理阶段的上下文——token、上下文窗口、注意力开销、位置偏差，以及围绕它们的上下文工程手段。不讨论模型训练、微调，也不涉及权重层面的知识存储。

1. 学习目标

读完这份材料后，你应该能够：

  1. 清晰区分"上下文窗口"与"上下文长度"这两个常被混用的词；
  2. 解释为什么长上下文的开销增长得比 token 数量更快；
  3. 说明"Lost in the Middle"现象，并据此调整 prompt 的信息排布；
  4. 面对一个塞不下或塞下也不准的场景，选对上下文工程手段（按需加载 / 压缩 / 缓存 / 记忆）。

2. 核心问题

带着这几个问题往下读，读完你应该能自己回答：

  1. 如果一个模型的上下文窗口是 100 万 token，是不是意味着我塞 100 万 token 进去它都能用好？
  2. 把整本手册塞进 prompt 让它回答一个细节问题，为什么常常不如只给它相关的两页？
  3. 上下文窗口越做越大，RAG（检索增强）是不是要过时了？

3. 个人解释

学这个概念之前，我把它当成一个纯粹的"容量问题"——窗口越大越好，不够就等下一代模型。学完之后，我认为它更像一个预算问题。

打个比方

上下文像一张办公桌的桌面。

  • 上下文窗口＝桌面的物理面积，决定了最多能摊开多少文件；
  • 上下文工程＝你怎么往桌上摆——摆什么、摆哪儿、什么时候把旧的收走；
  • 注意力预算＝你在同一时刻能真正"看进去"多少。

这个比方的关键在于：换一张更大的桌子，并不会让你同时读懂更多文件。桌面铺满了，你反而找不到刚才放在中间的那一页。Anthropic 在《Effective context engineering for AI agents》里用的说法是"注意力预算"——每加一个 token 都在花预算，目标是用最小的高信号 token 集合达成目的，而不是把所有可能相关的信息都堆上去。

我当初的误解

我曾经以为"窗口 = 能力"：模型标称 100 万 token，我就认为它能可靠处理 100 万 token 的信息。后来才分清——窗口是容量上限，不是可靠使用范围。模型"能接收"这些 token，和"能准确找到并利用其中某一条"，是两件不同的事。而后者会随着上下文变长而变差。

一个反例

假设你要让模型从一份 200 页的产品手册里回答"这款设备的保修期是多久"。

直觉做法：把 200 页全文塞进上下文，让它自己找。
实测常常更差：如果这条保修信息恰好落在中间某页，模型很可能"看漏"，甚至编一个数字。

更好的做法：先检索定位到"售后与保修"那一节（可能就两页），只把这部分放进上下文。信息总量从 200 页降到 2 页，准确率反而上升。这正是"Lost in the Middle"给出的经验事实，也是 RAG 至今仍然必要的根本原因之一——它不只是省钱，更是提准。

4. 核心机制 / 组成

四个基本概念

概念含义容易搞混的点
Token 模型处理文本的最小单位，介于"字符"和"词"之间，中文里经常 1 个字 ≈ 1 个 token 上下 计费和窗口限制都按 token 算，不按字数算；同一个中文句子，不同模型切出的 token 数可能不同
上下文窗口 单次请求能容纳的最大 token 数（通常含输入 + 输出） 这是上限，不是"可靠处理长度"，更不等于模型会自动用好
上下文长度 你这一次实际用了多少 token 日常说"上下文太长"指挥的是这个，不是窗口
KV Cache 缓存已算过的注意力键值，避免重复计算，是长对话能跑起来的关键优化 它省的是计算，省不了注意力本身的复杂度，也省不了显存

为什么长上下文"贵得不成比例"

Transformer 的核心是自注意力（Self-Attention）——序列里每个 token 都要和包括自己在内的所有 token 计算关联。这意味着开销随序列长度按 平方级（O(n²)）增长，而不是线性。*

这就是"上下文是最稀缺资源"这个说法的物理根源：把上下文长度翻倍，注意力部分的开销大约变成四倍。所以工程上追求的是信息密度，不是信息总量。

* 严格地说，原始自注意力的时间与空间复杂度为 O(n²·d)，n 为序列长度、d 为表示维度。现代实现通过 FlashAttention、稀疏注意力、KV 压缩等手段大幅降低了常数与显存占用，但"随长度增长快于线性"这个基本特性没有消失。

位置偏差：Lost in the Middle

Liu 等人在 TACL 2023 的论文中做了受控实验：把回答所需的信息放在上下文的不同位置，观察模型表现。结果是一条U 型曲线——

论文的措辞是：表现通常在相关信息出现在输入开头或结尾时最高，而当模型必须在长上下文的中间取用信息时显著下降——即使是被明确宣传支持长上下文的模型也一样。实验还发现，把一个关键文档放到中间，效果甚至可能不如不给任何文档。

上下文腐烂（Context Rot）

Anthropic 用"Context Rot"（上下文腐烂）描述另一个现象：随着上下文里的 token 增加，模型准确召回信息的能力单调下降。不是到了某个长度突然崩掉，而是渐进地变差——所有模型都躲不开，只是下降的斜率不同。

这一点很重要，因为它推翻了"窗口够大就万事大吉"的思路：性能是梯度式下滑的，所以精心安排上下文，比单纯扩大窗口更划算。

四种工程手段

手段做什么解决的问题
按需加载
(Just-in-time)		 不预先塞入全部数据，只维护"轻量指针"（文件路径、查询语句、链接），运行时按需取用 窗口容量不够；也避免无关信息稀释注意力
压缩
(Compaction)		 对话变长时，把较早的内容总结成一段摘要替换掉原文 长任务里历史消息无限增长
Prompt 缓存 把稳定不变的部分（系统提示、工具定义、长文档）标记出来跨调用复用 成本——重复计费的输入
记忆工具
(Memory)		 把需要跨会话保留的内容（用户偏好、上次结论）写到外部存储，下次读回 无状态——上下文天生不跨会话

关键瓶颈：不是窗口大小，而是"放进去"与"用得上"之间的落差。所有手段本质上都在做同一件事——把高信号的信息放进上下文，把低信号的挡在外面或写进外部存储。

5. 应用案例

用 grep / head / tail 分析大数据，而不是全量加载

  • 输入：一个体量远超上下文窗口的数据文件（日志、数据库导出），以及一个分析问题（如"异常发生在哪个时段"）。
  • 做了什么：不把文件读进上下文，而是让 Agent 用 Bash 命令（grep、head、tail）在文件上做定位和抽样，只把命中的片段取回上下文。
  • 产出：基于少量高信号片段得出的分析结论。
  • 为什么有效：Anthropic 在《Effective context engineering for AI agents》里把这种做法称为"just-in-time"上下文——维护轻量标识符（文件路径、查询），运行时再动态加载，并明确提到 Claude Code 就是用这种方式对大型数据库做复杂分析的。文章打的一个比方我觉得很到位：这更像人类——我们不背下整座图书馆，而是用文件系统、收件箱、书签来按需取回。
这个案例改变了我的一个默认习惯：以前遇到"信息太多塞不下"，第一反应是"换窗口更大的模型"；现在第一反应是"我为什么要把不需要的信息也放进去"。

6. 概念辨析

边界常见误用怎么判断
上下文窗口 vs 上下文长度 说"这个模型上下文很长"，其实想说的是窗口大；或者反过来 问：你在说"最大能装多少"还是"这次装了多少"？前者是窗口（模型的属性），后者是长度（这次请求的属性）
"能放进去" vs "能用上" 认为塞进去就等于模型会考虑，于是把资料全量灌入 长上下文里准确取用会下降（Lost in the Middle、Context Rot）。判断法：把关键信息换个位置再测一次，若答案变了，说明你之前只是运气好
上下文 vs 记忆 把两者混为一谈，以为"我记得上次说过"是模型自带的 上下文是单次请求内的临时输入，请求结束就没了；跨会话保留必须靠外部存储（记忆工具、文件、数据库）主动写回
窗口变大 vs 不需要工程 "窗口都 100 万 token 了，RAG 可以扔了" 窗口解决装不下，解决不了找不准和成本高。检索的价值一半是省 token，一半是提准——把高信号内容放到模型更容易用上的位置

7. 自测题

3–5 道，难度递增。先自己想，再展开答案。

★ 第 1 题 · 记忆

"上下文窗口"和"上下文长度"分别指什么？为什么这两个词不能混用？

查看答案

上下文窗口是单次请求能容纳的最大 token 数——它是模型的固有属性，是个上限；上下文长度是这一次请求实际用掉的 token 数——它随每次请求变化，是实际值。
为什么不能混：因为两者的对策完全不同。窗口不够是"模型选型"问题（换模型），长度过长是"上下文工程"问题（裁剪、检索、压缩）。把它们说混，往往会导致用错方法——比如为了"上下文太长"去换一个更大窗口的模型，结果费用上升、准确率没变。

★★ 第 2 题 · 理解

为什么长上下文的推理开销增长得比 token 数量更快？

查看答案

因为 Transformer 的自注意力机制要求序列中每个 token 与所有 token（含自身）计算关联，计算量随序列长度按平方级增长：长度翻倍，注意力部分开销约变为四倍。
补充两点，避免理解过头：① 现代实现用 FlashAttention、稀疏注意力、KV 压缩等大幅降低了常数因子和显存占用，但"快于线性"这个基本特性没消失；② KV Cache 主要省的是重复计算（已算过的键值不再重算），并不能把注意力本身的复杂度降下来。
这个机制是"为什么要把上下文当稀缺资源"的物理根源。

★★★ 第 3 题 · 应用

你要做一个"从 20 份技术文档中回答问题"的助手。方案 A：全部塞进上下文。方案 B：先检索出最相关的 3 份再塞入。你怎么选？需要考虑哪些因素？

查看答案

多数情况下选 B，但要按条件判断：
倾向 B 的理由：① 准确率——相关文档可能落在长上下文的"中间"，按 Lost in the Middle 的结论容易被漏掉；② 成本与延迟——token 数大幅下降；③ 稳定性——上下文越短，模型注意力越集中。
倾向 A 的理由：检索可能漏掉真正相关的文档（召回失败），而全量放入不会漏；如果文档总量不大、且问题的答案分散在多份文档需综合，全量更稳。
所以真正的判断依据是：你的瓶颈是"检索召回不准"还是"上下文太长导致找不准"。工程上常见的做法是两者结合——先检索缩小范围，再把结果按重要性放在上下文开头和结尾（避开中间），并对稳定的系统提示做缓存。
这道题的关键不是选 A 或 B，而是能说出"取决于哪个环节在失败"。

★★★★ 第 4 题 · 辨析

解释 Lost in the Middle 现象，并说明它对 prompt 排布有什么实际指导。

查看答案

现象：把回答所需的信息放在上下文的不同位置，模型表现呈 U 型曲线——放在开头或结尾时准确率最高，放在中间时显著下降。这是 Liu 等人（TACL 2023）在多样本文档问答和键值检索两个任务上的受控实验结论，而且即使是标称支持长上下文的模型也呈现同样模式，说明它不是窗口容量不够造成的，而是模型使用上下文的方式本身有位置偏好。
实践指导：
· 把最关键的信息放在开头或结尾，不要埋在长篇材料的中间；
· 如果必须给多份材料，按重要性排布，别让关键的那一份随机落在中间；
· 长文档考虑摘出关键段落而非整篇塞入；
· 验证方法：把关键信息换个位置重跑一遍，如果结果变了，说明你原来的成功可能只是位置运气。
注意：该实验测于 2023 年的模型，后续模型代际有所缓解但未消除，且幅度依赖具体模型——所以别把 U 型曲线当成固定常量，要针对自己用的模型实测。

★★★★★ 第 5 题 · 综合

有人说："模型上下文窗口都到 100 万甚至 200 万 token 了，RAG（检索增强）已经没用了。"请评价这个说法。

查看答案

这个说法把"装得下"当成了"用得好"，混淆了窗口容量与可靠使用范围。逐条拆：

① 准确率问题没有解决。窗口变大只保证 token 能被接收，不保证能被准确找到。Lost in the Middle 与 Context Rot 表明，上下文越长，模型准确取用信息的能力越差，而且是梯度式下滑。全量灌入反而可能让关键信息淹没在中间。
② 成本与延迟问题没解决。注意力开销随长度增长快于线性。每次请求都塞入海量 token，费用和响应时间都不可接受；即使做缓存，也只是缓解重复计费，不改变注意力本身的代价。
③ 数据规模问题没解决。企业知识库常常是百万级文档，永远超过任何窗口。窗口再大，也只是把"装不下"这条线的位置推后了一点。
④ 权限与时效问题没解决。检索层可以按用户权限过滤、按时间取最新版本；把全部资料灌进上下文，反而难以做细粒度的访问控制。

更准确的判断：窗口变大改变了两者的分工，而不是取消了一方。检索负责"在超大规模里定位候选"，长上下文负责"在有限候选里做综合推理"。合理架构是——先检索缩小范围，再按重要性排布放入上下文（避开中间），配合缓存与压缩控制成本。
凡是听到"某项技术让另一项技术过时了"这类绝对判断，先问一句：它解决的是原来的哪个瓶颈，剩下的瓶颈谁来解决？
