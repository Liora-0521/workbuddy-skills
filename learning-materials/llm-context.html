大模型的上下文

LLM 单次推理中能"看见"的最大文本长度，以 Token 计量，是大模型的"短期记忆容量"。

2. 核心问题

阅读时建议带着这些问题：

  • 为什么上下文窗口不是越大越好？背后的物理限制是什么？
  • 它的关键机制（自注意力、位置编码、KV Cache）里，缺哪一块模型就跑不起来？
  • 它和最像它的概念 RAG 区别在哪？什么场景该用 RAG 而不是扩窗口？
  • 它的边界是什么？窗口开到 2M Token 后还有哪些坑？

3. 个人理解

3.1 它是什么

上下文窗口（Context Window）是基于 Transformer 架构的大语言模型在单次推理中能处理的最大序列长度，以 Token 数计量。

我自己的理解：把它想成一块固定面积的黑板——你问的问题、AI 写的回答、之前的对话历史，都写在同一块黑板上。黑板写满了，最早的内容就被擦掉，AI 就"忘了"。这块黑板的面积，就是上下文窗口。

注意有两个容易混的词：

  • 上下文长度（Context Length）：模型架构能处理的最大序列长度（理论上限）；
  • 上下文窗口（Context Window）：实际推理时考虑的输入长度，≤ 上下文长度。

我当初的误解：以为"窗口 = 内存条"，越大越好。其实它更像注意力视野——越大视野越宽，但注意力越分散，关键信息反而容易被淹没（"Lost in the Middle"现象）。

3.2 核心机制 / 组成

  • Token：模型读写的最小单位。中文约 1.5-2 个汉字 = 1 Token；英文约 4 个字母 = 1 Token；标点、空格、emoji 都算。
  • 自注意力（Self-Attention）：每个 Token 都能"看见"序列中所有其他 Token，是窗口的物理基础。复杂度 O(n²)——长度翻倍，计算量变 4 倍。
  • 位置编码（Positional Encoding）：给 Token 加"顺序标签"，让无序的注意力知道谁在前、谁在后。RoPE / ALiBi / YaRN 都是不同方案。
  • KV Cache：推理时为已生成的 Token 缓存 K/V 向量，避免每生成一个 Token 就重算一遍所有历史——长上下文能落地的关键工程优化。
  • 位置编码外推：模型训练时只见过 4K Token，但通过位置编码的巧妙设计，能"外推"到 128K / 1M 仍保持低困惑度。

3.3 为什么这样设计

上下文窗口的演进是被三个物理约束倒逼出来的：

  1. 算力约束：自注意力是 O(n²)，窗口从 4K 到 128K 需要 1024 倍内存；
  2. 显存约束：KV Cache 与输入长度线性相关，长窗口推理时显存很容易爆；
  3. 位置编码泛化约束：原始 Transformer 的位置编码不能外推，必须重新设计（RoPE / YaRN）才能让短训练长度支撑长推理窗口。

所以每次窗口扩大，背后都是一组新工程突破（不是简单"参数调大"）。

4. 应用案例

案例：Google Gemini 1.5 Pro 用 2M Token 窗口"读完"整部电影

Google 在 2024 年演示过：把 2 小时电影《阿甘正传》的全部视频帧 + 字幕（折合约 1M Token）直接喂给 Gemini 1.5 Pro，然后问"影片最后 5 分钟主角说了什么"，模型能精确回答。

这件事背后的工程意义是：

  • 多模态统一窗口：视频帧、字幕都被转成 Token 序列，共享同一注意力空间；
  • 超长位置编码：Gemini 用的是自研的"Mixture of Experts + 超长 RoPE"组合，能稳定外推到 2M；
  • KV Cache 分页：2M Token 的 KV Cache 太大，必须用分页 + 量化才能装进显存。

这意味着原本需要做"视频抽帧 + RAG + 多轮对话"的复杂流水线，现在可以直接"全量送入"——但成本仍然极高，不能滥用。

来源：Gemini 官方页面、百度百科·上下文窗口。

5. 概念辨析

边界 1：上下文窗口 ≠ Token 数量

误用方式：把"我用了 50K Token 的窗口"当成"我读了 50K 个字"。实际上 Token ≠ 字——中文 1 Token ≈ 1.5-2 个汉字，英文 1 Token ≈ 0.75 个词，代码里 1 Token ≈ 几字符不等。

如何判断：用 tiktoken 等 tokenizer 实际跑一下，再换算成中文字数 / 英文字数。永远不要用"字数"估算成本。

边界 2：超长窗口 ≠ 信息全用得上

误用方式：以为 Gemini 1M Token 窗口 = 模型能用好 1M Token。事实上Lost in the Middle 现象明确说明：模型对开头和结尾的召回率高（~80-90%），对中间段召回率显著下降（~40-50%）。把关键信息塞在中间等于埋雷。

如何判断：重要信息要么放开头、要么放结尾；中间段只放"支撑材料"。或者改用 RAG 先做筛选，再送入模型。

边界 3：扩窗口 ≠ 替代 RAG

误用方式：因为 Gemini 有 2M 窗口，就觉得所有任务都可以"全量送入"，不需要 RAG。其实当文档总量远超窗口（如 50M Token 的法律合同库），仍必须用 RAG 先检索候选；超长窗口适合做"精细对比"，不适合做"大海捞针"。

如何判断：如果你的文档总量 < 窗口的 50%，可以全量送入；否则先 RAG 筛到 10-30%，再用长窗口做精细处理。

6. 自测问题

Q1（是什么）：用一句话定义上下文窗口。

答案：上下文窗口是 LLM 单次推理能处理的最大序列长度，以 Token 计量，决定了模型"短期记忆"的容量上限。

Q2（为什么）：为什么上下文窗口变大时算力需求呈平方级增长？

答案：因为 Transformer 的自注意力机制要为每个 Token 计算与其他所有 Token 的相关性分数，序列长度从 n 变 2n，注意力矩阵就从 n² 变 4n²，是 O(n²) 复杂度。

Q3（怎么用）：估算一段 1 万字的中文文档需要多少 Token？

答案：中文 1 Token ≈ 1.5-2 个汉字，1 万字 ≈ 1 万字 ≈ 5000-6700 Token；加上标点、段落、可能的 markdown 标记，实际约 6K-7K Token。可用 tiktoken 验证。

Q4（怎么区分）：上下文窗口 与 RAG 的核心区别是什么？

答案：上下文窗口是模型的内部容量（一次能"装多少"）；RAG 是外部检索机制（装不下时怎么补货）。两者互补——当总量能装下就用全量窗口，否则先用 RAG 缩小候选再送入。
