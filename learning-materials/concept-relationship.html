Agent × 大模型的上下文 × Skill

三个概念不是孤立的——上下文决定 Agent 能跑多远，Skill 决定 Agent 能做多专。

由 concept-learner Skill 生成 · 人工核查与修改 · 2026-09-04

1. 一句话总结

  • Agent 是运行时——能推理、能调用工具、能循环；
  • 大模型的上下文 是 Agent 的物理瓶颈——决定它能"记住"多少、"看到"多长；
  • Skill 是 Agent 的岗位手册——把"如何做某类事"打包成可复用的结构化指令。

关键观察：

  • Skill 和 Prompt 最终都会被加载进 上下文，参与 LLM 的推理；
  • 上下文 不是无限制的——它受 算力 / 显存 约束；
  • Agent 的循环每一步都在"消耗"上下文（系统提示 + 历史动作 + 工具结果）。

3.2 具体表现

窗口表现Agent 的工作影响工程对策
窗口太小（如 4K） 多轮对话失忆；长代码任务必须切片；Agent 循环跑不到 5 步就崩 RAG 压缩信息；短期记忆摘要；限制单步长度
窗口适中（如 32K-128K） 能装下中等代码库；中等复杂任务够用；Agent 循环可跑到 10-20 步 默认大多数 Agent 的工作区间
窗口很大（如 1M+） 能装整本书 / 整部电影；Agent 循环可跑 50+ 步；但Lost in the Middle 出现 重要信息放开头 / 结尾；用结构化提示；必要时配合 RAG

关键洞察：上下文窗口 ≠ 有效信息量。窗口大只是"能装"，能不能用好要看位置编码泛化能力（RoPE / YaRN）、任务设计（重要信息摆放位置）、以及 KV Cache 工程优化。

4.2 Skill 沉淀了哪些类型的知识

知识类型在 Skill 里的载体例子
领域术语 / 概念库 SKILL.md 正文 + references/ 本仓库的 concept-learner Skill 就沉淀了"如何系统学一个概念"的方法论
工作流 SOP SKILL.md 的"执行流程"章节 "客户投诉" Skill：先查订单 → 看历史 → 升级条件判断 → 通知
工具脚本（确定性操作） scripts/ 下的 Python / Bash "PDF 处理" Skill：pdf_rotate.py、pdf_merge.py
领域参考资料 references/ 下的 Markdown "SQL 调优" Skill：references/ 下放公司数据库 schema、历史慢查询案例
输出模板 assets/ 下的 PPT / HTML / Frontend 模板 "周报" Skill：assets/ 下放标准周报模板

关键洞察：Skill 的真正价值不是"让 Agent 更聪明"，而是把团队 / 个人的隐性知识变成显性资产。一个好的 Skill 写一次，能被几十个 Agent / 项目复用几个月 / 几年。

5. 三者的协同工作流

用一个真实例子（Cursor 编程 Agent）把三者串起来：

sequenceDiagram
    participant U as 用户
    participant A as Agent
(Cursor Composer)
    participant S as Skill
(代码规范 + 团队约定)
    participant L as LLM
(推理内核)
    participant C as 上下文窗口
(200K Token)
    participant T as 工具
(Read/Edit/Bash)

    U->>A: "把 login.py 改健壮点"
    A->>S: 语义匹配触发
    S->>C: 加载 SKILL.md
(团队代码规范 + 审查清单)
    A->>L: 把 Skill + 用户请求
+ 仓库结构塞入上下文
    L-->>A: 推理：要先读 login.py
    A->>T: Read(login.py)
    T-->>A: 返回文件内容（塞入上下文）
    L-->>A: 推理：password 字段没 trim()
    A->>T: Edit(login.py, 加上 trim())
    T-->>A: 修改完成
    A->>T: Bash(跑测试)
    T-->>A: 测试通过
    A->>U: 输出修改总结

三个概念各自扮演的角色：

  • Skill 在第 3-4 步登场：把"团队代码规范"注入上下文，让 Agent 知道"健壮"对你意味着什么；
  • 上下文窗口 在每一步都被消耗：系统提示 + Skill + 历史 + 工具结果 都要装得下；
  • Agent 是整个流程的调度者——它决定"现在该干什么"、"该调哪个工具"、"什么时候停"。

6. 易混淆边界速查表

对比维度Agent大模型的上下文Skill
本质 运行时（runtime） 物理容量（capacity） 指令包（instruction package）
形态 软件 / Agent SDK 数字（Token 数） Markdown 文件（SKILL.md）
谁来用 开发者 / 用户 LLM 内部 Agent 内部
类比 员工本人 员工的工作记忆容量 员工的岗位手册
边界 Agent ≠ Workflow；Agent ≠ Copilot 窗口 ≠ Token 数；大 ≠ 信息全用得上 Skill ≠ Agent；Skill ≠ Command；Skill ≠ MCP

7. 实践建议

  1. 做 Agent 之前，先想清楚上下文够不够——多轮 / 长任务的 Agent 必须配大窗口或 RAG；
  2. 做 Skill 之前，先想清楚沉淀什么知识——一次性 prompt 不要做成 Skill，只有"会反复用的方法"才值得；
  3. 三个一起用：让 Agent 跑、让上下文扛住、让 Skill 注入专业能力——三者缺一不可。
