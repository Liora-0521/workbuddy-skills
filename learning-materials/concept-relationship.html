概念关系图谱

Agent × 大模型的上下文 × Skill

三个概念不在同一层：上下文是工作台，Agent是干活的人，Skill是架子上随时可取的手册。

本文范围：只描述这三者在"单个 LLM 智能体系统"内部的分工与依赖关系。不展开多智能体协作、不讨论模型训练层面的上下文扩展技术。

1. 一句话总结

  • 上下文是工作台——模型单次推理能看到的全部输入，也是它最贵的资源；
  • Agent 是运行主体——在循环里读取上下文、决定动作、调用工具的那一方；
  • Skill 是知识包——装在文件夹里的程序性知识，模型按需取用。
一句话串起来：上下文决定 Agent 能想多远，Skill 决定 Agent 能做多专。前者是能力的天花板，后者是专业度的来源。

2. 三者各自的定位

这张图里有三条关键边，分别对应三种影响：

  • Agent → 上下文（实线，每轮都读）：Agent 无法直接"思考"，它的一切判断都基于上下文里的内容。上下文之外的东西，对它而言不存在。
  • Skill → 上下文（虚线，触发后注入）：Skill 本身不是常驻的，它通过"触发 → 读取 SKILL.md → 内容进入上下文"这条路径产生影响。
  • 上下文 → Agent（虚线，预算约束）：上下文是有限且昂贵的，它反过来限制 Agent 能走多远。

4. 上下文如何影响 Agent 的工作

很多人把"上下文"理解成一个中性的容器——装什么它就照单全收。实际不是。上下文从三个层面主动地塑造 Agent 的行为：

中间的信息容易被忽略"] CTX --> COST["③ 成本层面

只能早早收尾"] B1 --> BEH["Agent 的实际行为"] B2 --> BEH B3 --> BEH

① 容量：硬性天花板

窗口是硬约束。超出就直接失败，没有"将就一下"的余地。更隐蔽的影响是：Agent 会为了腾出空间而裁剪历史，而被裁掉的那一段里，可能正好有它后面要用的线索。

② 质量：能放进去 ≠ 能用上

Liu 等人（TACL 2023）的实验显示，相关信息位于上下文开头或结尾时表现最好，位于中间时显著下降——即使在标称支持长上下文的模型上也是如此。这意味着 Agent 的失败常常不是"它不知道"，而是"信息就在上下文里，但它没取用"。

这条对 Agent 尤其致命：Agent 是循环的，中间步骤的工具返回值往往就落在上下文的"中间地带"。如果它在第 8 步忽略了第 4 步取回的关键信息，后面的推理就会建立在错误前提上——这正是"多轮之后开始跑偏"的常见机制。Anthropic 用"上下文腐烂"（Context Rot）描述这种随 token 增加而单调下降的召回能力。

③ 成本：越长的上下文越贵

自注意力要求每个 token 与所有 token 计算关联，开销随长度按平方级增长。所以"多跑几轮、每轮都带上完整历史"这种朴素做法，成本会迅速变得不可接受。这也是压缩、子智能体隔离上下文、把中间结果写进文件这些手段存在的理由。

我的结论：把上下文当作"带边际收益递减的稀缺资源"来管，而不是当作免费的记事本。Agent 的可靠性问题，很大一部分其实是上下文管理问题。

5. Skill 如何沉淀可复用的任务知识

Skill 要解决的是：同一个团队反复交代同一套做法，但每次对话都是全新的。prompt 是一次性的，说完就散；Skill 把它沉淀成文件，从此可按需取用。

sequenceDiagram autonumber participant U as 用户 participant SP as 系统提示 participant AG as Agent participant SK as Skill 目录 Note over SP: 启动时：每个 Skill
只加载 name + description
（约 100 token/个） U->>AG: "帮我生成这周的周报" AG->>SP: 拿请求去匹配各 Skill 的 description SP-->>AG: 命中 weekly-report AG->>SK: bash 读取 SKILL.md SK-->>AG: 返回核心步骤（<5k token） Note over AG: 指令进入上下文，开始执行 AG->>SK: 仅在需要核对口径时，读 references/kpi.md SK-->>AG: 返回该文件片段 AG->>SK: 运行 scripts/aggregate.py SK-->>AG: 只返回运行结果
（脚本代码不进上下文） AG-->>U: 输出周报

这张时序图里有四个设计要点，我认为是 Skill 最值得学的地方：

  1. 知识在没被用到时不占任何上下文。启动时只有一行简介常驻，这是"装几百个 Skill"仍然可行的原因。
  2. 触发靠 description，不靠用户敲命令。所以 description 必须同时写清"能做什么"和"何时用它"——这是 Skill 会不会被自动用起来的决定性因素。
  3. 用文件边界切分"总是需要"和"偶尔需要"。核心流程留在 SKILL.md，细则移到 references/。Anthropic 的 PDF Skill 就是把这招用在表单填写说明上的。
  4. 确定性操作交给脚本。脚本代码不进入上下文，只有输出进入——既省 token，又比让模型逐步计算更可靠。
所以我理解 Skill 的本质不是"存知识"，而是按使用频率给知识分层，再用文件系统的边界把层次固定下来。它是给 Agent 用的、可版本管理的程序性记忆。

6. 常见误解

误解为什么错更准确的说法
"上下文窗口越大，Agent 越强" 窗口只解决"装得下"，解决不了"找得到"和"用得起"。长上下文里准确取用会下降，成本还会陡增 窗口是必要条件，不是充分条件。上下文的组织方式比容量更影响表现
"Agent 只要模型够强就行" 控制流、工具设计、反馈回路才是 Agent 区别于单次调用的本质；工具描述含糊时，强模型同样选错工具 Agent 是架构选择。模型是其中一个变量，不是全部
"Skill 就是写得更规范的 prompt" 漏掉了按需加载、文件系统结构、捆绑脚本这几个关键差异 Skill 是可复用、分层加载、可版本管理的能力包；prompt 是对话级的一次性指令
"有了 Skill 就不需要 MCP 了"（或反过来） 两者解决的问题不同：一个管"会不会做"，一个管"连不连得上" MCP 是连接协议，Skill 是知识封装，实践中常配合使用
"Skill 内容写得越全越好" 正文一旦触发就整体进入上下文，越臃肿越稀释关键指令，等于放弃了渐进式披露的收益 按使用频率分层：常用的留在正文，偶尔用的搬出去

7. 自测题

3–5 道，难度递增。先自己想，再展开答案。

★ 第 1 题 · 记忆

用一句话分别说明上下文、Agent、Skill 在这套体系里的角色。

查看答案

· 上下文是工作台——模型单次推理能看到的全部输入，也是它最贵的资源；
· Agent 是运行主体——在循环中读取上下文、决定动作、调用工具的那一方；
· Skill 是知识包——装在文件夹里的程序性知识，模型按需取用。
为什么值得背这三句：因为它们分别回答了"能看到什么""该做什么""该怎么做"三个不同层次的问题——混淆层次是理解这三者时最常见的错误。

★★ 第 2 题 · 理解

为什么说"上下文决定 Agent 能跑多远"？请从机制上解释，不要只说"因为窗口有限"。

查看答案

"窗口有限"只是第一层。完整地看，上下文从三个机制上限制 Agent：
① 容量上限——超出窗口请求直接失败，没有折中空间。这迫使 Agent 裁剪历史，而裁掉的部分可能正是后面要用的线索。
② 取用质量随长度下降——Lost in the Middle 表明，位于上下文中间的信息容易被忽略。Agent 是循环结构，中间步骤的工具返回值恰好落在"中间地带"，一旦被忽略，后续推理就建立在错误前提上——这正是"多轮之后开始跑偏"的典型机制。
③ 成本随长度增长快于线性——自注意力开销近似随序列长度平方增长，"每轮都带完整历史"的做法会迅速变得不可承担，于是长循环在经济上不可行。
所以更准确的说法是：上下文不只是"天花板"，它还通过降低取用质量和抬高成本这两种方式，主动地塑造 Agent 会怎么做。

★★★ 第 3 题 · 应用

你做了一个 Agent，前 7 步都正常，到第 8 步之后开始反复出错。从这三个概念的角度，你怀疑哪些原因？按什么顺序排查？

查看答案

最可疑的方向是上下文，其次是循环设计，最后才是模型能力。建议排查顺序：
① 先查上下文（最可能）——前几步正常说明模型能力够用。第 8 步开始出错，典型原因是中间步骤的工具返回值落到了上下文的"中间地带"被忽略（Lost in the Middle），或者上下文里累积了过量的低信号内容，把关键信息稀释掉了，也可能触发了压缩机制导致早期关键约束被总结丢失。
做法：把第 8 步前后的完整上下文打出来看——关键约束还在不在？在第几位？如果把关键信息挪到开头或结尾重跑，结果是否改善？
② 再查循环设计——有没有设置停止条件？第 8 步附近是否进入了某种重复模式（例如反复调同一个工具）？错误是否在累积放大？
③ 然后查 Skill（如果有）——如果该任务依赖某个 Skill，检查它是否在第 8 步之后没有被正确触发，或正文里的指令是否被后续上下文淹没。
④ 最后才考虑换模型。把换模型作为第一反应，往往会掩盖真正的工程问题。
这道题的关键判断："前几步正常"这个信息本身就排除了"模型能力不足"这一大类解释，把矛头指向了随轮次累积的上下文状态。

★★★★ 第 4 题 · 辨析

Skill 和 MCP 是什么关系？请构造一个需要两者配合的场景，并说明各自承担什么。

查看答案

关系：层次不同、不互相替代。MCP 是连接协议，解决"Agent 够不够得着"外部系统的问题——它把工具、数据源、服务以标准方式暴露给 Agent。Skill 是知识封装，解决"这类任务该怎么做"的问题——它把流程、口径、最佳实践打成可复用的包。一个是接口层，一个是知识层。
配合场景——"数据周报助手"：
· MCP 负责连得上：通过 MCP 把数据仓库、BI 系统、邮件服务接入 Agent，让它有能力查询数据、拉取图表、发送邮件。
· Skill 负责会做：用一个 weekly-report Skill 规定——该查哪几张表、时间范围怎么取、指标口径对照 references/kpi.md、聚合计算跑 scripts/aggregate.py、输出的版式规范是什么。
如果只有 MCP 没有 Skill：Agent 连得上数据库，但每次都要重新摸索该查什么、怎么算，口径可能每次都不一样。
如果只有 Skill 没有 MCP：Agent 知道流程，但拿不到数据，只能干说步骤。
一句话区分：MCP 让 Agent"够得着"，Skill 让 Agent"做对路"。这也是为什么两者在实践中通常是叠加使用，而不是二选一。

★★★★★ 第 5 题 · 综合

设计一个"合同审阅助手"（输入一份可能上百页的合同，输出风险点清单）。请说明上下文、Agent、Skill 三者各承担什么角色，并给出你的上下文开销控制方案。

查看答案

角色分工：
· Agent＝运行主体。它是循环的：定位条款 → 比对规则 → 标记风险 → 复核 → 汇总。它决定下一步读哪一段、要不要再查一遍、什么时候收尾。
· 上下文＝工作台，也是最需要精打细算的资源。合同上百页，绝不可能整份放进上下文——不仅超窗口风险高，还会因 Lost in the Middle 让关键条款被淹没。
· Skill＝知识包。把"怎么审合同"沉淀下来：审查维度、风险分级标准、输出格式、以及公司特有的红线条款。

具体设计：
① Skill 侧（分层）：
· SKILL.md 只放核心流程与输出规范（常用的，留在正文）；
· references/risk-rules.md 放完整风险规则库与公司红线条款（体量大、按需查）；
· references/output-format.md 放不同受众的报告模板（仅特定场景需要）；
· scripts/ 放确定性操作，如按条款编号切分文档、统计风险条目、格式校验。
② 上下文侧（按需加载 + 隔离）：
· 不整份读入——先用脚本或检索定位候选条款，只把命中的段落拉进上下文；
· 用文件当外部记忆——每审完一节，把结论写进中间文件，而不是全部堆在对话历史里；
· 子智能体隔离——大范围筛查派子智能体去做，只让它把相关片段返回主流程，避免把整份材料的上下文带回来；
· 压缩与缓存——稳定的系统提示、规则库前几节做缓存；对话变长时对早期轮次做总结压缩。
③ Agent 侧（控制流）：
· 设计明确停止条件（如已覆盖全部条款类别或达到最大轮次）；
· 关键判断（是否触发红线）保留人工复核环节——合同场景的误判代价高，不能完全交给自主循环。

④ 位置优化：汇总阶段把最高风险项放在输出的开头，规则约束放在提示的开头与结尾，避开容易被忽略的中间位置。

这道题想通的标志：你会发现"上下文开销控制"不是单点技巧，而是 Skill 分层设计 + Agent 循环设计 + 按需加载三者协同的结果——这正是三个概念互相咬合的地方。
