Agent

以 LLM 为大脑、能自主规划 + 调用工具 + 持续执行的 AI 系统。

1. 学习目标

学完本文后，你应当能够：

  1. 用一段话向同行解释 Agent 是什么、不是什么，并指出它和普通 LLM 的关键差异；
  2. 独立完成一个能调 1-2 个工具的简单 Agent（如天气查询 + 邮件发送）；
  3. 区分 Agent 与 LLM / Workflow / Copilot / Subagent 这 4 个常被混用的概念；
  4. 指出 Agent 的 1-2 个使用边界（比如"确定性任务反而是 Workflow 更划算"）；
  5. 读懂 OpenAI / Anthropic 官方关于 Agent 设计的核心段落。

2. 核心问题

阅读时建议带着这些问题：

  • Agent 解决的是什么问题？为什么纯 LLM 聊天不能解决？
  • 它的 4 大模块（LLM / 规划 / 记忆 / 工具）里，缺哪一块它就只是"伪 Agent"？
  • 它和最像它的概念 Workflow 区别在哪？什么场景该用 Workflow 而不是 Agent？
  • 它的成本边界在哪？每多一轮循环，token 和延迟怎么涨？

3. 个人理解

3.1 它是什么

Agent = LLM（推理内核）+ Planning（规划）+ Memory（记忆）+ Tools（工具调用）。它是把 LLM 从"会聊天"升级为"会办事"的关键架构。

我自己的理解：很多人第一反应会把 Agent 当成一个"更聪明的 AI"。其实关键不是"更聪明"，是有手有脚。一个 LLM 再强也只能输出文字；给它装上能跑命令、查数据库、写文件的工具，它才能真的改变环境状态。这也是为什么 OpenAI 在官方指南里把 Agent 定义为"独立代表用户完成任务（independently accomplish tasks on your behalf）"——重心在"完成任务"上，不是"生成回答"上。

我当初的误解：以为 Agent 就是"能记住多轮对话的 LLM"。事实上"记忆"只是 Agent 的一部分，更核心的是"循环"——它不是输入一次输出一次，而是 观察 → 推理 → 行动 → 观察 → ... 的无限循环，直到任务完成或主动终止。

3.2 核心机制 / 组成

  • LLM（推理内核）：负责理解指令、做决策、选择工具。GPT-4 / Claude / Llama 都是"可塞进 Agent 的大脑"。
  • Planning（规划模块）：把"订机票"这类大目标拆成"搜索 → 比价 → 选航班 → 填表 → 支付"的小步骤，常用技术是 Chain-of-Thought / Tree-of-Thought / ReAct。
  • Memory（记忆系统）：短期记忆（当前会话上下文）+ 长期记忆（向量数据库 / 外部知识库），解决"窗口只有 N Token，装不下所有历史"的物理限制。
  • Tools（工具集）：Agent 与外界交互的接口——搜索 API、读写文件、执行 shell、调用业务 API，每个工具都有标准化定义（name / description / parameters）。
  • Controller / Loop（控制器）：管理"观察 → 规划 → 行动 → 反馈 → 状态更新"的循环调度，决定何时停止、何时回退、何时把控制权交回人类。

工业实现上会简化成三件套：Model + Instructions + Tools（如 OpenAI Agents SDK），规划与记忆由 SDK 隐式提供。但概念上仍然是四大模块。

3.3 为什么这样设计

Agent 不是被某个人"天才设计"出来的，它是过去 5 年 LLM 三次能力突破倒逼出来的产物：

  1. Function Calling 出现（2023）——LLM 第一次能稳定输出结构化指令，工具调用才变成可能；
  2. 长上下文窗口（2024）——能装下整个对话历史，Agent 才不用每次都从零推理；
  3. 强推理模型（o1/o3/Claude 3.7 thinking, 2025）——LLM 能可靠地"反思自己的错"，规划才能跑长链。

没有这三点，任何一个 Agent 都会在第三步就崩掉。

4. 应用案例

案例：Cursor（AI 编程 IDE）里的 Composer 2 Agent

Cursor 在 2026 年 3 月发布的 Composer 2 模型内置了 200K Token 的上下文窗口和工具调用能力，使 Agent 能在用户的代码仓库里：

  • 用 ListFiles 工具读仓库结构；
  • 用 Read / Grep 工具定位相关代码；
  • 用 Edit 工具修改源文件；
  • 用 Bash 工具跑测试验证修改是否正确；
  • 若测试失败，自动反思错误并重写代码。

这背后是一个完整的 Agent 循环：观察仓库 → 推理要改哪些文件 → 用工具读 → 编辑 → 测试 → 失败则反思 → 重做。整个过程对用户只暴露一次"接受 / 拒绝"的最终决策点。

来源：Cursor 官方博客、百度百科·上下文窗口（提及 Composer 2 的 200K 窗口）。

5. 概念辨析

边界 1：Agent ≠ 更"聪明"的 LLM

误用方式：以为换更先进的 LLM（比如 GPT-5 vs GPT-4）就能让 Agent 更强。事实上 Agent 的瓶颈往往在工具集的设计和循环的稳健性，而不是 LLM 的 IQ。换个 GPT-3.5 + 设计良好的工具集，常常比 GPT-5 + 烂工具集更好用。

如何判断：如果你的"Agent"只是一次 prompt → 一次回答，没有工具调用、也没有循环，那它不是 Agent，只是一个普通的 LLM 调用。

边界 2：Agent ≠ 永远比 Workflow 好

误用方式：把所有自动化任务都丢给 Agent，觉得"AI 更灵活"。对于确定性 + 高频 + 容错低的任务（订单状态查询、报表生成、对账），Workflow 反而更便宜、更稳定、更可审计。Anthropic 在《Building Effective Agents》里专门强调：能用 if-else 解决的就别上 Agent。

如何判断：如果任务的成功率 > 95%、路径 < 5 步、错误成本高，用 Workflow；如果成功率 < 70%、路径可能很长、需要处理模糊输入，用 Agent。

边界 3：Agent ≠ Subagent ≠ Copilot

误用方式：把"Subagent"当主 Agent 的替代品，或者把 Copilot 当 Agent 的低配版。其实是不同的设计模式：

  • Copilot：用户主导，AI 辅助（Cursor 早期模式、GitHub Copilot Chat）；
  • Agent：AI 主导，用户审批（Cursor Composer 2、Devin）；
  • Subagent：主 Agent 调度的、有独立上下文的子任务执行者（多 Agent 系统里的角色）。

如何判断：用户主动操作每一步 → Copilot；用户授权后 AI 跑全程 → Agent；多个 Agent 互相调用 → Multi-Agent（含 Subagent）。

6. 自测问题

Q1（是什么）：用一句话定义 Agent。

答案：Agent 是以 LLM 为推理内核、结合规划 + 记忆 + 工具调用，能自主完成多步骤任务的 AI 系统。

Q2（为什么）：Agent 相比单纯使用 LLM，最大的改进点是什么？

答案：能改变环境状态——通过工具调用真实地读写文件、调 API、操作浏览器，而不是只输出文本；并且能多步循环，在每一步观察反馈后调整下一步行动。

Q3（怎么用）：给出一个具体场景，说明如何使用 Agent 解决。

答案（示例）：用户说"项目里有个登录页 bug，帮我修一下"。Agent 循环：(1) 用 ListFiles 列仓库；(2) 用 Read 读 login.py；(3) 用 Grep 找相关函数；(4) 推理出 bug 根因是 password 没 trim()；(5) 用 Edit 修改；(6) 用 Bash 跑测试；(7) 输出修复总结。

Q4（怎么区分）：Agent 与 Workflow 的核心区别是什么？

答案：Workflow 是预设的确定性流程（if-else + 顺序），执行路径固定；Agent 是基于 LLM 推理的动态流程，能处理未定义分支。简单说：Workflow 是流程图，Agent 是会看情况走流程图的员工。
