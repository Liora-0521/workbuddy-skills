概念学习指南

Agent（智能体）

Agent 的核心不是"模型更聪明"，而是让模型在一个循环里自己决定下一步做什么，直到任务完成。

本文范围：只讨论 LLM-based Agent——以大语言模型为决策核心、在带工具的环境中循环行动的智能体。不涉及强化学习领域的 RL Agent，也不展开多智能体协作与博弈。

由 concept-learner Skill 生成 · 人工核查于 2026-09-10

1. 学习目标

读完这份材料后，你应该能够：

  1. 用"控制流由谁决定"这把尺子，区分 Agent 与 Workflow；
  2. 拆解出 Agent 的最小构成（模型 / 工具 / 循环），并指出其中的关键瓶颈；
  3. 面对一个具体任务，判断它该不该用 Agent，而不是默认上 Agent；
  4. 解释 ReAct 为什么要让"推理"和"行动"交替出现。

2. 核心问题

带着这几个问题往下读，读完你应该能自己回答：

  1. 如果我把一个固定的三步流程写死在代码里，让模型只负责每一步的文案，这算 Agent 吗？
  2. Agent 的"自主"带来了什么代价？为什么这个代价常常被低估？
  3. 给模型接上更多工具，Agent 会更强吗？

3. 个人解释

我对 Agent 的理解经历过一次明显的转向。

最初我以为 Agent 是"能力更强的模型"——好像模型够聪明，Agent 自然就成立。后来读 Anthropic 那篇《Building effective agents》才意识到，他们把话说得很直接：在 LLM 应用里，成功的实现往往不是用了复杂框架，而是用了简单、可组合的模式。Agent 的关键变量不在"模型有多强"，而在"循环怎么设计、工具怎么定义"。

换句话说：Agent 是一种架构选择，不是一次模型升级。

打个比方

Workflow 像传送带：物料从哪来、经过哪几道工序、在哪一站停下，全是事先焊死的。Agent 像骑手：你只说"把这份文件送到 XX 路 5 号"，路线、绕行、遇到封路怎么办，由他自己判断。

这个比方能推出一件事：传送带在稳定重复的任务上又快又便宜，因为它不会"想多了"；骑手在路径不可预测的任务上才有价值——你很难提前把路线焊死。这也正是 Anthropic 的建议：先用最简单的方案，只在确实需要时才增加复杂度。

我当初的误解

我原以为"Agent = 模型 + 一堆工具"，工具越多越强。结果发现真正的分水岭是循环：模型能不能拿到环境的真实反馈（工具返回结果、代码运行输出、测试是否通过），并据此修正下一步。没有反馈回路的"工具调用"，只是一次性的函数调用，不是 Agent。

一个反例

"把这段话翻译成英文"——这是一个单步任务，没有中间状态、不需要环境反馈、路径完全确定。给它套一个 Agent 循环，只会增加延迟和 token 消耗，还要承担模型"想多了"、自己加戏的风险。

反过来说：凡是能用确定性代码写死流程的任务，就不该用 Agent。这句话我现在的使用频率，比"怎么让 Agent 更强"高得多。

4. 核心机制 / 组成

把 Agent 拆到最小，只有三件事——但第三件最容易被忽略：

组件作用备注
模型（决策） 读当前上下文，决定下一步做什么：思考、调工具，还是收尾 Anthropic 把 Agent 简化为"LLM 在循环中自主使用工具"
工具（行动） 与外部世界交互的接口：检索、读写文件、执行代码、调 API 工具的文档质量直接决定 Agent 可靠性——这一步常被当成"配角"，其实是主角之一
循环（反馈） 把工具的真实返回结果写回上下文，驱动下一轮决策 这是"Agent"和"一次函数调用"的分界线；ReAct 把它形式化为 Thought → Action → Observation

与 Workflow 的分界

Anthropic 的切分方式我觉得最干净：

  • Workflow：LLM 和工具通过预定义的代码路径被编排——流程由工程师写死；
  • Agent：LLM 动态决定自己的流程与工具使用——流程由模型现场决定。

所以判断标准不是"用没用大模型"，而是：控制流握在谁手里。

ReAct：循环的最小形态

Thought:      我需要先确认这个项目的测试命令是什么
Action:       read_file("package.json")
Observation:  "scripts": { "test": "vitest run" }
Thought:      好，跑测试看当前状态
Action:       run_bash("npm test")
Observation:  3 failed, 12 passed  → 根据失败信息决定下一步

ReAct 论文的实验很说明问题：在 HotpotQA 上，纯推理（Chain-of-Thought）会因为不接触外部信息而产生幻觉；纯行动（只有工具调用、没有思考）则缺了规划，工具调得乱七八糟。两者交替，效果最好。

而且每个 Thought / Action / Observation 都是可读的——出问题时你能定位到是哪一步想歪了，这是端到端黑箱方案给不了的。

关键瓶颈：不是模型智力，而是错误累积与上下文预算。Agent 每多走一轮，前面某一步的小偏差都可能被放大；同时整个轨迹（工具定义 + 返回结果 + 历史消息）都在吃掉上下文。所以真实工程里，压缩历史、用子智能体隔离上下文、把中间结果写进文件，往往比"换个更强的模型"更有效。

5. 应用案例

编码 Agent：用测试结果当"地面真值"

  • 输入：一个自然语言描述的代码任务（例如把某个仓库里失败的测试修好），可能涉及多个文件的修改。
  • 做了什么：Agent 自己探索代码库找到相关文件 → 改代码 → 运行测试 → 读取失败信息 → 再改。循环往复，直到测试通过或达到停止条件。
  • 产出：一组通过测试的代码改动。
  • 为什么有效：关键在于反馈是可验证的。测试通过 / 不通过是客观信号，不需要人来判断，Agent 可以自己判断进度。Anthropic 在《Building effective agents》的附录里把这类任务列为 Agent 最合适的场景之一，并提到他们用 coding agent 处理 SWE-bench 这类任务；同一篇里也强调，Agent 自主性带来更高成本和错误累积风险，建议先在沙箱环境里充分测试并设置护栏。
这个案例给我的启发不是"Agent 能写代码"，而是：选对任务比调好模型更重要。有清晰成功标准、能自动验证、能形成反馈回路的任务，才是 Agent 的舒适区。

6. 概念辨析

边界常见误用怎么判断
Agent vs Workflow 把写死的三段流程（LLM 只负责填文案）也叫 Agent，宣称"我们上了 Agent" 问一句：步骤数量、顺序、是否继续，由代码决定还是由模型决定？代码决定＝Workflow
Agent vs 聊天机器人 有对话界面就认为是 Agent 看有没有工具 + 循环 + 环境反馈。只输出文字、不改变外部状态的，是聊天机器人
Agent vs 单次工具调用 把一次 function calling 包装成 "Agent" 看有没有多轮自主决策：调完工具后，是否根据结果决定继续、换策略或停止
"模型更强 → Agent 更强" 只盯着换模型，忽视工具接口设计 Anthropic 明确把"精心设计 agent-computer interface（工具文档与测试）"列为三大原则之一。工具描述含糊时，再强的模型也选错工具

7. 自测题

3–5 道，难度递增。先自己想，再展开答案。

★ 第 1 题 · 记忆

用一句话说出 Agent 与 Workflow 的区别，并指出判断依据。

查看答案

区别在于控制流归谁。Workflow 由预定义代码路径编排 LLM 与工具，流程是工程师写死的；Agent 由 LLM 动态决定自己的流程和工具使用。判断依据是：步骤数量、顺序、何时停止，是代码决定（Workflow）还是模型决定（Agent）。
为什么要背这一句：因为大多数"我们做了 Agent"的说法，一问这个就露馅——很多其实是 Workflow。

★★ 第 2 题 · 理解

ReAct 为什么要让"推理"和"行动"交替出现？只有行动（纯工具调用）不行吗？

查看答案

不行，两者缺一不可。只有行动会缺少规划：模型不知道该用哪个工具、什么时候停、结果怎么组合，容易乱调；只有推理（Chain-of-Thought）则会脱离外部事实，拿训练数据里的记忆硬编答案，在需要新信息的任务上产生幻觉。
ReAct 让推理为行动提供方向、行动为推理提供依据。论文中在 HotpotQA 上，纯 CoT 因不接触外部环境而出错，纯行动则无法综合出最终答案，而交替进行的 ReAct 表现最好。此外它还有额外收益：Thought/Action/Observation 都是人类可读的，便于定位是哪一步想歪。

★★★ 第 3 题 · 应用

现在有一个任务："从 10 万行服务器日志里，找出所有包含 ERROR 的行并按出现频率排序。"应该用 Agent 吗？

查看答案

不该。这是一个规则完全确定、单步可完成的任务——一条 grep ERROR access.log | sort | uniq -c | sort -rn 就能搞定，结果确定、可复现、成本近乎为零。
用 Agent 的代价：多轮推理的延迟与 token、模型可能"发挥创意"写出不严谨的过滤条件、结果不可复现。Anthropic 的原则正是"先找最简单的方案，只在必要时才增加复杂度"。
真正该考虑 Agent 的版本是："日志里似乎有异常，帮我找出根本原因"——这时路径不可预测，需要反复假设、验证、调整，才有循环的价值。

★★★★ 第 4 题 · 辨析

Agent 的"自主性"带来了哪些具体代价？为什么实践中强调先在沙箱里跑？

查看答案

至少三类代价：
① 成本与延迟——多轮循环意味着多次模型调用和工具执行，比单次调用贵得多；
② 错误累积——链条越长，早期的小偏差越可能被后续步骤放大，最终结果偏离很远；
③ 不可预测的行为——模型可能采取你没想到的操作路径，甚至做出难以撤销的动作（删文件、force push）。
所以要在沙箱里跑：把 Agent 放在影响可控、可回滚的环境里，先观察它在真实任务上的行为模式和失败方式，再逐步放开权限。Anthropic 也建议配合"停止条件"（如最大迭代次数）来维持控制。

★★★★★ 第 5 题 · 综合

有人主张："给 Agent 接更多工具，它就更强。"请指出这个说法的漏洞，并给出改进方向。

查看答案

漏洞在于把工具当成"能力加法"，忽视了选择成本。工具集合膨胀后会出现两个问题：
① 决策歧义——多个工具功能重叠或命名含糊，模型难以判断该用哪个。Anthropic 指出这是最常见的失败模式之一，并给了一个很实用的判据：如果人类工程师都说不清某个场景该用哪个工具，就不能指望 AI 说得清；
② 上下文占用——工具定义本身要进上下文，工具越多，留给任务本身的预算越少，还会稀释模型注意力。

改进方向：
· 收敛工具集：追求"最小可用集合"，功能不重叠，每个工具的职责边界清晰；
· 写好工具文档：参数命名明确、说明何时该用、何时不该用、失败时怎么处理；
· 分层与按需加载：不是所有工具都要常驻上下文（这也正是 Skill 的渐进式披露思路）；
· 用评估说话：加工具前后跑同一组评测，用任务成功率而不是"工具数量"衡量收益。
