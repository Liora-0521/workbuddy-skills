概念学习指南

Skill（智能体技能）

Skill 是装在文件夹里的程序性知识：模型平时只知道它存在，需要时才翻开细读。

本文范围：只讨论 Anthropic 提出并已开放为标准的 Agent Skills（以 SKILL.md 为核心的文件夹格式）。不讨论传统软件工程中的"技能矩阵"，也不展开各平台在实现细节上的差异。

1. 学习目标

读完这份材料后，你应该能够：

  1. 写出一个合法 Skill 的最小结构，并说明 name 与 description 各自的约束；
  2. 解释渐进式披露的工作原理，以及它为什么能让"装几百个 Skill"不撑爆上下文；
  3. 判断一份内容该放进 SKILL.md 正文、放进 references/，还是写成 scripts/；
  4. 说清 Skill 与 Prompt / Agent / MCP / Command 的分工边界。

2. 核心问题

带着这几个问题往下读，读完你应该能自己回答：

  1. Skill 和我平时写的 prompt 模板，本质差别到底在哪？
  2. 为什么我可以同时装几百个 Skill，而上下文不会爆？
  3. 同样是把能力交给 AI，什么时候用 Skill，什么时候用 MCP？

3. 个人解释

我最初把 Skill 理解成"更规范的 prompt 模板"——无非是把提示词写进一个 md 文件。真正读进去之后，我认为这个理解漏掉了最关键的一点：Skill 是一个会被"按需打开"的文件系统结构，而不是一段会被完整读入的文本。

Anthropic 自己的比喻我很喜欢：给 Agent 写一个 Skill，就像给新员工写一份入职指南。你不会把公司的全部制度塞进新人脑子里，而是给他一个放着手册的书架——先告诉他"有哪些手册"，需要时再去翻具体那本。

打个比方

Skill 像公司里的操作手册架：

  • 架子上每本手册的书脊（名称 + 一句话简介）你随时能看到 → 这是第 1 级：元数据；
  • 伸手抽出某一本，翻开正文 → 这是第 2 级：SKILL.md 主体；
  • 正文里写着"详细参数见附录 C"，你再去翻附录 → 这是第 3 级：捆绑资源。

关键在于：没被翻开的手册，不占你现在的注意力。这就是 Skill 能横向扩展的根本原因。

我当初的误解

我以为 Skill 就是个"知识容器"，当然是写得越全越好——把团队的规范、常见问题、代码片段全塞进 SKILL.md。后来意识到这恰恰破坏了 Skill 的核心设计：一旦触发，正文会整体进入上下文。写得越臃肿，每次触发就吃掉越多的上下文预算，还把真正关键的指令稀释掉了——等于花了渐进式披露的钱，用出了"全量加载"的效果。

一个反例

想象一个"处理 PDF"的 Skill。它有两类内容：

  • 提取文本的核心流程——几乎每次都要用；
  • 表单填写的详细步骤——只在填表时才用。

把两类内容都写进 SKILL.md：每次提取文本，都要白白读一遍表单填写的说明。
Anthropic 在介绍 Agent Skills 时正是拿这个例子说明：把填表说明拆到单独的 forms.md，核心文件就能保持精简，模型只在真的要填表时才去读那一份。

4. 核心机制 / 组成

结构：一个文件夹

my-skill/ ├── SKILL.md # 必需：YAML 元数据 + Markdown 指令 ├── scripts/ # 可选：可执行脚本 ├── references/ # 可选：按需加载的参考文档 └── assets/ # 可选：模板、资源文件

最低限度只需要一个 SKILL.md。其余目录都是"需要时才加"。

SKILL.md 的元数据

---
name: pdf-processing
description: Extract text and tables from PDF files, fill forms, merge
  documents. Use when working with PDF files or when the user mentions
  PDFs, forms, or document extraction.
---
字段约束要点
name 最多 64 字符；只能小写字母、数字、连字符；不能含 XML 标签；不能用保留字 相当于"书脊上的书名"
description 不能为空；最多 1024 字符；不能含 XML 标签 最关键的一个字段——模型靠它判断该不该触发这个 Skill
description 必须同时回答两件事：这个 Skill 能做什么 + 什么时候该用它。只写第一件，模型不知道该在什么场景调它；这正是"写好了 Skill 却不触发"的最常见原因。

渐进式披露：三级加载

级别加载时机Token 开销内容
第 1 级：元数据 启动时始终加载（写进系统提示） 每个 Skill 约 100 token frontmatter 里的 name 和 description
第 2 级：指令 Skill 被触发时加载 通常少于 5k token SKILL.md 主体——工作流程、最佳实践、指导
第 3 级及以上：资源 按需加载 被访问前为零 捆绑的参考文件、脚本、模板、数据集

流程是这样的：启动时系统提示里只有每个 Skill 的名称和简介 → 用户请求进来，模型拿请求去和各个 description 匹配 → 命中后，用 bash 把对应的 SKILL.md 读进上下文 → 如果正文里引用了其他文件（如 FORMS.md），再用额外的 bash 命令去读 → 正文里提到的脚本，通过 bash 执行，只有输出进入上下文。

两个值得单独记住的设计：

  • 脚本的代码不进上下文，只有运行结果进。让模型跑一个排序脚本，比起让它逐 token 生成排序结果，既便宜又确定——所以确定性操作用代码，灵活判断用指令。
  • 捆绑内容几乎没有上限。因为文件在没被读取前不消耗任何 token，Skill 里可以放完整的 API 文档、大型示例集，没用到就不产生开销。

关键瓶颈：不在存储，而在 description 的匹配准确度。第 1 级元数据是模型决定"要不要打开这本书"的唯一依据——描述写得太宽，会到处误触发；写得太窄，该用的时候想不起来。Skill 的扩展性由渐进式披露保证，但它的可用性由 description 决定。

5. 应用案例

Anthropic 的 PDF Skill：把"偶尔才用"的部分拆出去

  • 输入：用户上传 PDF，提出需求（提取文本、填表单、合并文档等）。
  • 做了什么：模型启动时只看到该 Skill 的 name + description；当用户请求涉及 PDF 时触发，读取 SKILL.md；如果任务只是提取文本，就按核心流程执行，完全不读表单相关的文件；只有当任务真的是"填表单"时，才额外读取 forms.md。
  • 产出：完成的 PDF 操作结果。
  • 为什么有效：Anthropic 在《Equipping agents for the real world with Agent Skills》中把 PDF 处理作为贯穿全篇的例子，明确指出：把填表指令移到单独文件，让 Skill 作者能够保持核心精简，并相信模型只在需要填表时才去读那份文件。这就是渐进式披露在真实产品里的落地方式——用文件边界来切分"总是需要"和"偶尔需要"的知识。
这个案例给我的最大启发是那句"像为新员工写入职指南"。写 Skill 时我现在的习惯是：先问"哪些是每次都要知道的"，把它们留在 SKILL.md；其余全部搬出去。

6. 概念辨析

边界常见误用怎么判断
Skill vs Prompt 把 Skill 当成"存在文件里的提示词模板" Prompt 是对话级、一次性的指令；Skill 是可复用、按需加载、基于文件系统的能力包，还带捆绑资源和脚本。判断法：换个会话还要重新粘贴一遍的，是 prompt
Skill vs Agent 把两者当成同一层的东西来比较 层次不同：Agent 是运行主体（在循环里决策、调工具），Skill 是它调用的能力包。Skill 给 Agent 提供"怎么做某类事"的程序性知识，但不自己发起循环
Skill vs MCP 认为两者功能重叠，选一个就行 解决的问题不同：MCP 是连接协议，负责让 Agent 够得着外部工具和数据源（"能不能连上"）；Skill 是知识打包，负责告诉 Agent 这类任务该怎么做（"会不会做"）。实践中两者常配合使用
Skill vs Command 以为 Skill 也要用户显式敲命令才会生效 触发方式不同：Command 通常由用户显式调用；Skill 由模型根据 description 自动匹配当前请求。所以 description 写得准不准，直接决定 Skill 会不会被自动用起来

7. 自测题

3–5 道，难度递增。先自己想，再展开答案。

★ 第 1 题 · 记忆

一个 Skill 的最小必需结构是什么？元数据里哪两个字段是必需的？

查看答案

最小结构是一个包含 SKILL.md 的文件夹——只需要这一个文件，scripts/、references/、assets/ 都是可选。SKILL.md 必须以 YAML frontmatter 开头，其中 name 和 description 是必需字段。
为什么要记住"最小"：因为很多人一上手就搭一堆目录，反而让结构复杂化。Anthropic 的设计是"需要时才加"，从最简单的一文件开始，等真的需要拆分时再拆。

★★ 第 2 题 · 理解

什么是渐进式披露？它为什么能让"同时装几百个 Skill"而不撑爆上下文？

查看答案

渐进式披露是指信息分级别、按需加载，而不是一次全部读入：
· 第 1 级——元数据（name + description），每个 Skill 约 100 token，启动时始终加载；
· 第 2 级——SKILL.md 正文，通常少于 5k token，只在 Skill 被触发时加载；
· 第 3 级及以上——捆绑的参考文件和资源，被访问前开销为零；脚本则只把运行结果送进上下文，代码本身不进入。
为什么能装几百个：因为未触发时，每个 Skill 只贡献约 100 token 的元数据——几百个 Skill 也就是几万 token 的常驻开销，远小于把它们的正文全部常驻。而一旦触发，只有那一个 Skill 的内容进入上下文。
本质：用"总是需要 / 偶尔需要 / 极少需要"的层次切分，把上下文预算花在当下真正相关的内容上。

★★★ 第 3 题 · 应用

你要写一个"生成团队周报"的 Skill。以下内容分别应该放在哪里：①每周固定要走的 5 个步骤；②公司 KPI 指标口径的完整定义表（30 页）；③把数据按周聚合的 Python 脚本；④只有在生成"季度总结版"时才用到的额外格式规范。

查看答案

① 放进 SKILL.md 正文——这是每次执行都需要的核心流程，属于"总是需要"的第 2 级内容。
② 放进 references/——30 页定义表体量太大，且并非每次都要逐条查。放成独立文件，模型在需要核对某个指标口径时再去读，避免每次生成周报都吃掉大量上下文。
③ 放进 scripts/——这是确定性操作。交给脚本执行有两个好处：结果可靠（不依赖模型逐步生成计算步骤）、省上下文（脚本代码本身不进上下文，只有运行结果进）。
④ 放进 references/ 的单独文件（例如 quarterly-format.md），并在 SKILL.md 里写明"生成季度版时另读此文件"——这正是 PDF Skill 拆出 forms.md 的思路：用文件边界隔离"偶尔才需要"的知识。
共同原则：按使用频率分层，而不是按内容重要性排序。

★★★★ 第 4 题 · 辨析

Skill、Agent、MCP、Command 这四者各自处在什么位置？请说清分工边界。

查看答案

可以用"主体—协议—知识—入口"四个角色来定位：
· Agent＝运行主体。它是在循环中自主决策、调用工具的那一方。它决定"现在要做什么"，并在过程中调用 Skill。
· MCP＝连接协议。解决"够不够得着"的问题——让 Agent 以标准方式接入外部工具、数据库、服务，是能力的接口层。
· Skill＝知识打包。解决"会不会做、按什么规矩做"的问题——把程序性知识、流程、最佳实践打成可复用的包，是能力的知识层。
· Command＝触发入口。通常由用户显式调用；而 Skill 靠 description 被模型自动匹配。
关键区分：MCP 让 Agent"连得上"某个系统，Skill 让 Agent"知道该怎么用它做事"。两者不替代，常配合：例如通过 MCP 连上数据仓库（连得上），再用一个 Skill 规定"生成周报时该查哪些表、按什么口径算"（会做）。
容易犯的错：把 Skill 和 MCP 当成二选一。它们回答的是不同的问题。

★★★★★ 第 5 题 · 综合

有同事把公司所有规范（代码风格、命名约定、发布流程、周报模板、客服话术……）全部写进了一个 SKILL.md 的正文，理由是"这样 AI 一次就掌握全部规则"。请指出问题，并给出重构方案。

查看答案

问题诊断——这个做法等于放弃了渐进式披露：
① 触发即全量加载。正文一旦被触发就整体进入上下文。他说的"一次掌握全部"，实际是"每次都要读完全部"——无论当前任务是写代码还是写周报，都要为其余四类无关规范付出 token 成本。
② 稀释注意力。无关内容占比越高，真正相关的指令被淹没得越厉害——这与上下文越"嘈杂"、模型越容易失焦的规律一致。
③ description 无法准确描述。一个包罗万象的 Skill，很难写出"做什么 + 何时用"都准确的描述，结果是该触发时不准、不该触发时误触发。
④ 违背"入职指南"的隐喻。Anthropic 的比喻是给新员工一个书架，不是把全套制度塞进他脑子。

重构方案：
· 按任务域拆成多个 Skill：code-style、release-process、weekly-report、customer-support……每个 Skill 的 description 各管一个场景，模型的匹配也更准；
· 每个 Skill 内部再分层：核心流程留在 SKILL.md；体量大的细则（完整命名表、话术全集）放 references/，按需读取；
· 确定性操作脚本化：例如发布流程里的检查项，写成 scripts/ 下的脚本，只把结果送进上下文；
· 共享内容做单一来源：多个 Skill 都要用的通用条款，抽成共享文件引用，避免复制多份导致不同步；
· 用真实任务验证：分别测试"该触发的场景是否触发"和"每次触发的 token 开销"，用数据而不是感觉来判断拆分是否合理。
一句话总结：Skill 的扩展性来自拆，不是来自堆。
