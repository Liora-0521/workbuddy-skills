Skill

装在 Agent 里的"岗位手册"，把"如何做某类事"打包成可分享的结构化指令。

由 concept-learner Skill 生成 · 人工核查与修改 · 2026-09-04

1. 学习目标

学完本文后，你应当能够：

  1. 用一段话向同行解释 Skill 是什么，并指出它和 Agent / Command / MCP 的边界；
  2. 独立创建一个含 SKILL.md + references/ 的简单 Skill 并装进 Claude Code 试用；
  3. 区分 Skill 与 Agent / Command / Subagent / Rule / MCP Server 这 5 个易混概念；
  4. 指出 Skill 的 1-2 个使用边界（比如"上下文窗口紧张时不要装 20 个 Skill"）；
  5. 读懂 SKILL.md frontmatter 的 name / description / agent_created 字段含义。

2. 核心问题

阅读时建议带着这些问题：

  • Skill 解决的是什么问题？为什么 Agent 自己不够用？
  • 它的 4 个可选部分（SKILL.md / scripts / references / assets）里，缺哪一块它就只是个"prompt 文件"？
  • 它和最像它的概念 Agent 区别在哪？什么场景该用 Agent 而不是 Skill？
  • 它的边界是什么？装多少 Skill 会让上下文爆掉？

3. 个人理解

3.1 它是什么

Skill 是一种以 SKILL.md 为核心的结构化指令包，给 Agent 提供针对特定任务类型的标准化工作流程、知识与最佳实践。

我自己的理解：把 Agent 想象成一个什么都能干的实习生，Skill 则是递给他的《岗位操作手册》——给他《代码审查手册》，他就成了"代码审查专员"；给他《SQL 调优手册》，他就成了"SQL 调优专员"。同一份手册可以在不同的 Agent（Claude Code / Codex CLI / Gemini CLI）间共享——这是 Skill 最大的杠杆。

我当初的误解：以为 Skill 是"给 Agent 的插件 / API"。其实 Skill 是纯文本 Markdown，不需要服务器、不需要权限、不需要 SDK——只要放在 ~/.claude/skills/ 或 .workbuddy/skills/ 下，Agent 启动时就会发现它。

3.2 核心机制 / 组成

  • SKILL.md（必需）：Skill 的核心文件。YAML frontmatter（name + description 决定触发）+ Markdown 正文（工作流指令）。
  • scripts/（可选）：可执行脚本（Python / Bash）。用于确定性操作（如 PDF 旋转、格式转换），可不读入上下文直接执行。
  • references/（可选）：参考文档（数据库 schema、API 文档、政策文件）。按需加载，避免 SKILL.md 过于臃肿。
  • assets/（可选）：输出资产（logo、PPT 模板、前端脚手架）。不读入上下文但参与最终产物。
  • 渐进式披露（Progressive Disclosure）：三层加载——metadata（~100 词，恒在）→ SKILL.md 正文（<5K 词，触发时加载）→ 资源（按需）。这是 Skill 能"装很多"的关键工程设计。
  • 语义触发：与 /command 的显式触发不同，Skill 由语义匹配自动触发——用户说"这段代码太乱了"，Agent 会自动调用代码格式化 Skill。

3.3 为什么这样设计

Skill 是被"通用 Agent 不够专"这个痛点逼出来的：

  1. 通用 Agent 在每个领域都是 60-70 分——它知道 SQL 是什么，但不如 DBA 调得好；知道代码审查，但不如资深工程师挑得准；
  2. Prompt 工程不能跨对话复用——同一个团队今天写的好 prompt，明天换个项目就没了；
  3. 传统 SDK / 插件门槛太高——不是每个会写代码的人都能发布 SDK，但每个人都能写 Markdown。

Skill 把"领域能力"的载体从"SDK / API"降维到"文档 / Markdown"，是 AI 工具平民化的关键一步。

4. 应用案例

案例：Anthropic 官方 Claude Skills + Claude Code 实战

Anthropic 在 2025 年 10 月推出 Skills 概念，并把官方示例 Skill 直接挂在 github.com/anthropics/skills，包含：

  • PDF Skill：让 Agent 能正确读取、合并、提取 PDF 内容（包含 scripts/ 下的 pdf_rotate.py 等脚本）；
  • Doc Skill：让 Agent 按 Anthropic 的格式规范生成 Word / Markdown 文档；
  • Brand Guidelines Skill：让 Agent 在写内容时自动遵循品牌指南（assets/ 下放 logo、字体）。

开发者只需要 git clone 到 ~/.claude/skills/，重启 Claude Code 就能用——不需要任何 SDK / API key。

本仓库的 concept-learner Skill 也是同样的设计：放在 .workbuddy/skills/concept-learner/，WorkBuddy 启动时自动发现，调用时按 frontmatter 里的 description 语义匹配触发。

来源：Claude Skills Explained — Anthropic、Claude Skills vs Agents — findskills.co。

5. 概念辨析

边界 1：Skill ≠ Agent

误用方式：以为"我装了一个 Skill，所以我的 Claude 变成另一个 Agent 了"。事实上 Skill 是指令文件（告诉现有 Agent 怎么做），不是运行时（能推理、能执行）。脱离 Agent 的 Skill 没有任何作用。

如何判断：如果删掉 Skill，Agent 仍然能跑（只是少了某个专项能力），说明它是 Skill；如果删掉就没法跑，那它是 Agent（或 Agent 的核心组件）。

边界 2：Skill ≠ Command（Slash Command）

误用方式：把 Skill 当成 Command 的高配版。其实触发方式完全不同：

  • Command：用户必须显式输入 /cmd 才运行；
  • Skill：用户说"代码太乱了"，Agent 自动匹配运行。

如何判断：用户是否需要记忆命令名？需要 → Command；不需要（语义触发）→ Skill。简单提示词封装用 Command；复杂能力封装用 Skill。

边界 3：Skill ≠ MCP Server

误用方式：把 Skill 和 MCP 当成同一层。事实是正交的两层：

  • MCP Server：给 Agent 提供工具和数据接入能力（让 Agent 能做 X，比如查数据库）；
  • Skill：给 Agent 提供流程和知识（让 Agent 知道何时 / 怎么做 X，比如"客户投诉时先查订单再升级"）。

如何判断：如果缺了它 Agent 就无法访问外部资源 → MCP；如果缺了它 Agent 还能跑，只是不专业 → Skill。

边界 4：装太多 Skill 会撑爆上下文

误用方式：因为 Skill "好装"，就一口气装 20 个。每个 Skill 的 frontmatter（~100 词）会始终在上下文里，SKILL.md 正文（<5K 词）会在被触发时加载。装 10 个 Skill ≈ 始终占 1K Token，被触发时还可能再占 50K。

如何判断：把"我现在会用到的" Skill 留 3-5 个；其余归档到一个 skills-archive/ 目录，需要时再启用。

6. 自测问题

Q1（是什么）：用一句话定义 Skill。

答案：Skill 是一种以 SKILL.md 为核心的结构化指令包，为 Agent 提供特定任务类型的工作流、知识与最佳实践，通过渐进式披露管理上下文消耗。

Q2（为什么）：Skill 相比传统 Prompt 的优势是什么？

答案：可跨对话复用、可跨 Agent 共享（Claude Code / Codex CLI / Gemini CLI 通用）、可语义触发（不必记忆命令名）、可分层加载（不爆上下文）。

Q3（怎么用）：给出一个具体场景，说明如何用 Skill 解决。

答案：给团队做"代码审查 Skill"——把团队多年沉淀的审查规范（命名、安全、可测性、性能）写成 SKILL.md（含 examples + checklists），放在 .workbuddy/skills/code-reviewer/。Claude Code 启动时会自动发现它，每次写完代码 Agent 都会自动按这份手册审查。

Q4（怎么区分）：Skill 与 Command 的核心区别是什么？

答案：Command 是显式触发（用户输入 /cmd）、封装简单提示词；Skill 是语义触发（Agent 自动匹配）、封装复杂能力（含 scripts / references / assets）。
