# 概念学习资料生成 Skill (concept-learner)

## 一、适用场景

这个 Skill 解决的是**从"听说过"到"讲得清、用得上、分得开"**的落差。

**触发**（满足任一）：

- 用户说"用 concept-learner 学习 X"或 `/concept-learner X`；
- 用户想系统掌握某个技术 / 学术 / 业务概念，并要一份**能存下来**的资料；
- 用户想为团队或个人沉淀"概念入门手册"，之后可直接分享 HTML 文件。

**不触发**：

- 只是查一句话定义 → 直接问答即可；
- 用户要的是**读**一份已有资料，而不是**生成**一份新资料。

**默认边界**：每次只处理一个概念。若用户一次给多个（如"学 Agent 和 RAG"），先确认是一次生成两份，还是先做其中一个。

---

## 二、输入信息

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `concept` | string | ✅ | 概念名，中英文均可，如 `Agent`、`RAG`、`Transformer`、`Skill`、`注意力机制` |
| `audience` | enum | ❌ | 目标读者：`beginner`（默认）/ `intermediate` / `advanced` |
| `focus` | string | ❌ | 侧重点，如"工程实现"、"理论基础"、"行业应用" |
| `output_dir` | path | ❌ | 默认 `learning-materials/`；文件名 `<slug>.html` |
| `slug` | string | ❌ | 未指定时由概念名推导：转小写、空格与特殊字符转连字符（`大模型的上下文` → `llm-context`） |

**概念边界必须先确认**。若 `concept` 存在歧义（例如"Agent"可能指 LLM Agent、也可能是强化学习 Agent），Skill 应主动追问，而不是自行假设。

---

## 三、生成步骤

按顺序执行，**每一步都不可跳过**。

### Step 1 — 划定范围

在动笔前先声明本文讨论什么、不讨论什么。例：

> 本文只讨论 **LLM-based Agent**（以大模型为决策核心、在循环中调用工具的智能体），不涉及强化学习领域的 RL Agent，也不展开多智能体博弈。

把这句话写进 HTML 的开头，避免资料变成"什么都说一点"的百科词条。

### Step 2 — 检索并**核查**资料源

1. 用 `WebSearch` 找核心定义、权威共识、最新进展；
2. 必要时用 `WebFetch` 读取原始页面，确认标题与内容对得上；
3. **逐条验证链接可访问性**（HTTP 状态码检查），剔除 404 / 403 / 需要登录的链接；
4. 至少 3 条可点击链接，其中至少 1 条为**一手来源**（官方文档、论文原文、标准规范）；
5. 检索不到就**少写**，绝不编造 URL。

> 引用前必须确认：链接可打开、页面标题与所引内容一致、来源注明访问日期。

### Step 3 — 写学习目标与核心问题

- **学习目标** 3–5 条，用"学完后能 **做** X"，而不是"能**知道** X"；
- **核心问题** 3–5 个，是读者读完后**应该能自己回答**的问题，用来牵引阅读。

### Step 4 — 写个人化解释（本 Skill 的重点）

这是最容易写成"百科复述"的一步，必须刻意避免：

- 用自己的话重述，**不整段照搬**检索结果或 AI 对话原文；
- 至少包含一处**类比**、一处**反例**、一处"**我当初的误解**"；
- 解释"**为什么这样设计**"，而不只是"它是什么"；
- 允许并鼓励保留判断和态度（"我认为这个说法被高估了，因为……"）。

### Step 5 — 拆解核心机制或组成

把概念拆成可记忆的结构：

- 用"组件 + 关系"的方式呈现（列表、表格或图）；
- 标出**哪个组件是瓶颈 / 关键路径**；
- 给出一个最小可理解的计算或流程示例。

### Step 6 — 给一个具体应用场景

- 场景必须**真实可验证**：有具体公司 / 产品 / 论文 / 代码；
- 说明四件事：输入是什么 → 做了什么 → 产出什么 → 为什么有效；
- 避免"某公司用 X 提升了效率"这类无法核查的表述。

### Step 7 — 辨析容易混淆的边界

至少 3 条。每条写成：

> **边界**：本概念到哪儿为止 → **误用**：常见怎么用错 → **判断**：怎么快速区分

### Step 8 — 设计自测题（3–5 道，难度递增）

**硬性要求**：

| 序号 | 难度 | 考查层次 | 典型问法 |
| --- | --- | --- | --- |
| 第 1 题 | ★ | 记忆 / 复述 | 它是什么？由哪几部分组成？ |
| 第 2 题 | ★★ | 理解 / 解释 | 为什么这样设计？不这样会怎样？ |
| 第 3 题 | ★★★ | 应用 / 判断 | 给定场景，该不该用它？怎么用？ |
| 第 4 题（可选） | ★★★★ | 辨析 / 迁移 | 它和 X 的边界在哪？换个条件还成立吗？ |
| 第 5 题（可选） | ★★★★★ | 综合 / 批判 | 设计一个方案，或者指出某个说法的漏洞 |

规则：

- 题目数量 **3–5 道**，必须**难度递增**（用 ★ 标注）；
- 每题答案放在 `<details>` 里，读者先想后看；
- 答案要解释**为什么**，不能只给结论。

### Step 9 — 写入 HTML

- 输出 `learning-materials/<slug>.html`；
- **单文件、内嵌 CSS**，双击即可在浏览器打开；
- 如果用到 Mermaid 关系图，引用本地 `vendor/mermaid.min.js`，**不要用 CDN**（断网或沙箱环境下会渲染失败）；
- 页脚注明：由 concept-learner Skill 生成于 YYYY-MM-DD ＋ 人工核查说明。

### Step 10 — 自检（**强制**）

对照第六节的清单逐项打勾。**未通过不得交付**。

---

## 四、输出结构

生成的 HTML 固定包含以下章节，顺序不可调整：

| # | 章节 | 内容要求 |
| --- | --- | --- |
| 1 | 学习目标 | 3–5 条"能做 X" |
| 2 | 核心问题 | 3–5 个引导问题 |
| 3 | 个人解释 | 带类比、反例、个人误解的原创叙述 |
| 4 | 核心机制 / 组成 | 组件 + 关系 + 关键瓶颈 |
| 5 | 应用案例 | 真实可验证的一个场景 |
| 6 | 概念辨析 | ≥3 条边界与误用 |
| 7 | 自测题 | 3–5 道，难度递增，答案可折叠 |
| 8 | 参考来源 | 已核查的可点击链接 + 访问日期 |

> 若生成的是"概念关系"类资料（多个概念之间的关系），第 3–6 节可替换为：概念定位、关系图（Mermaid）、协同工作流、常见误解，其余章节保持不变。

模板见 `references/template.html`。**仅可改写文案，不可增删或调换章节**。

---

## 五、资料来源要求（硬性规则）

1. **真实**：每条链接都能打开，标题与内容一致；
2. **可核查**：公开可访问，无需登录；
3. **不编造**：禁止出现占位域名或臆造 URL；
4. **优先一手**：官方文档 / 论文原文 / 标准规范 > 二手转述 > 个人博客；
5. **标注日期**：易变动的页面（官方博客、文档）注明访问日期；
6. **宁缺毋滥**：找不到合格来源时，减少引用数量，并**明确写出"此点未找到一手来源"**。

## 六、自检要求（强制清单）

- [ ] 章节 1–8 齐全且顺序正确？
- [ ] 开头已声明概念边界（讨论什么 / 不讨论什么）？
- [ ] 学习目标用"能做"而非"能知道"？
- [ ] 个人解释含类比 + 反例 + 个人误解，且无整段照搬？
- [ ] 核心机制拆出了组件与关键瓶颈？
- [ ] 应用案例有具体公司 / 产品 / 论文 / 代码，可验证？
- [ ] 概念辨析 ≥3 条，且每条含"边界 / 误用 / 判断"？
- [ ] 自测题 **3–5 道且难度递增**，每题有 `★` 标注与折叠答案？
- [ ] 每道自测题的答案解释了"为什么"？
- [ ] 参考来源**逐条 HTTP 验证通过**，并注明访问日期？
- [ ] HTML 单文件可独立打开，无 404 资源（Mermaid 用本地 `vendor/`）？
- [ ] 移动端阅读正常（无横向溢出）？
- [ ] 文件名符合 `learning-materials/<slug>.html`？

任何一项不通过，修改后重新自检。
