# 大模型的上下文

> **大模型在单次推理中能"看见"并处理的文本长度上限，以 Token 计量，是大模型的"短期记忆容量"。**

**通俗解释**：把上下文窗口想象成一块固定大小的黑板——你问的问题、AI 写的回答、之前的对话历史，都写在同一块黑板上。黑板写满了，最早的内容就会被擦掉，AI 就"忘了"。上下文窗口就是这块黑板的最大面积。

---

## 1. 概念定义

- **正式定义**：上下文窗口（Context Window）是基于 Transformer 架构的大语言模型（LLM）**单次推理中能够处理的最大序列长度**，以 Token（词元）数计量。它决定了模型可同时参考的历史对话、文档或代码的最大跨度。
- **通俗定义**：LLM 的"短期记忆"上限——决定了 AI 一次能"读完"多长的内容。
- **关键术语**：Context Window、上下文长度、Token、Attention Complexity、位置编码、RoPE、YaRN、FlashAttention。

> 注意区分两个概念：**上下文长度**是模型架构能处理的最大序列长度（理论上限），**上下文窗口**是实际推理时考虑的输入长度（≤ 上下文长度）。

## 2. 核心原理

### 原理 1：注意力机制的平方复杂度（O(n²)）
Transformer 自注意力的计算成本随序列长度呈**平方增长**——序列长度翻一倍，计算量变四倍，显存需求也近似翻四倍。  
*为什么这样*：自注意力要为每个 Token 计算与其他所有 Token 的相关性分数，序列长度从 4K 涨到 128K，注意力矩阵就从 4K×4K 涨到 128K×128K，显存和算力爆炸。

### 原理 2：Token 是计量的最小单位
LLM 不是按"字"或"词"读文本，而是按 **Token**（词元）读。中文约 1.5-2 个汉字对应 1 个 Token；英文约 4 个字母对应 1 个 Token。  
*为什么这样*：Token 化（Tokenization）让模型用统一的数值化方式处理任意语言，是 LLM 能泛化到多语言的根本。

### 原理 3：位置编码决定"能不能用满"窗口
窗口大小不只由架构决定，还取决于训练时的位置编码方案（RoPE、ALiBi 等）能否**外推**到更长序列。没有良好外推能力的模型，即使窗口声明 128K，在 64K 之后性能也会骤降。  
*为什么这样*：注意力机制本身是"无序的"（只看权重不看位置），必须靠位置编码告诉模型"谁在前、谁在后"；位置编码的泛化能力直接决定模型能否真正用满窗口。

### 原理 4：超长上下文存在"注意力稀释"
即便窗口支持百万 Token，模型对中间和靠后位置的注意力也会被分散，关键信息容易被淹没（所谓"Lost in the Middle"现象）。  
*为什么这样*：注意力是 softmax 归一化的，序列越长每个 Token 分到的权重越低；这不是 bug，是当前注意力机制的固有局限。

## 3. 关键组成

- **Token**：模型读取和生成的最小单位，是上下文的"原子"。
- **自注意力机制（Self-Attention）**：让每个 Token 看见序列中所有其他 Token，是上下文窗口的物理基础。
- **位置编码（Positional Encoding）**：为 Token 提供顺序信息，决定模型能否外推到训练长度之外。
- **KV Cache**：推理时为已生成的 Token 缓存 K/V，避免重复计算，是长上下文推理能落地的关键工程优化。
- **多模态扩展**：图像 / 音频 / 视频也被转换为 Token 序列，共享同一注意力空间。
- **上下文窗口大小**：模型能处理的最大 Token 数（如 4K、128K、200K、1M、2M）。

## 4. 应用场景

- **场景 1：长文档处理** —— 一次性"读入"整本书 / 完整代码库 / 长篇合同，做摘要、问答、翻译。  
  例：Gemini 1.5 Pro 演示过用 2M Token 窗口读完整部电影《阿甘正传》并回答细节问题。
- **场景 2：多轮对话** —— 让 AI 记住整段历史对话，避免"聊了 5 轮就忘了开头"的失忆感。
- **场景 3：代码库理解与重构** —— 把整个仓库塞进上下文，让模型做跨文件重构、依赖分析、Bug 定位。  
  例：Cursor Composer 2 用 200K 窗口做 AI 编程。
- **场景 4：检索增强生成（RAG）的替代方案** —— 当文档总量能塞进窗口时，直接"全量送入"比 RAG 更准；但超过窗口仍需 RAG。
- **场景 5：Agent 任务执行** —— Agent 的每一步推理都需要把"任务描述 + 历史动作 + 工具结果"全部塞进上下文，决定了 Agent 能连续执行多少步。

## 5. 具体例子

### 例子 1：上下文窗口容量的演进

```
GPT-3.5       → 4K Token   （约 3000 个汉字）
GPT-4         → 8K / 32K  Token
GPT-4o        → 128K Token
Claude 3.5    → 200K Token
Gemini 1.5 Pro → 2M Token   （约 150 万汉字，能装下整部小说）
```

每代窗口的扩展都依赖位置编码外推（RoPE → YaRN）、稀疏注意力、KV Cache 优化等工程突破。

### 例子 2：长文档问答的"丢中间"现象

```
假设窗口 100K Token，把以下三段关键信息按位置摆放：

[位置 0-2K]    ：关键信息 A（开头）
[位置 50K-52K] ：关键信息 B（中间）
[位置 98K-100K]：关键信息 C（结尾）

实验观察：模型对 A、C 的召回率 ≈ 80-90%；对 B 的召回率 ≈ 40-50%。
这就是 "Lost in the Middle"——长上下文不是简单的"装得多"，还要会"找得到"。
```

### 例子 3：上下文窗口 vs RAG 的取舍

```
任务：分析 1000 份法律合同（共 50M Token）

方案 A：扩展窗口到 50M → 一次性送入
  优点：模型能全局比较，召回率高
  缺点：算力成本极高（O(n²)），推理延迟长，注意力稀释严重

方案 B：RAG 先检索 50 份相关合同（50K Token）再送入
  优点：成本低、延迟短、可解释
  缺点：检索召回率决定上限，可能漏掉关键文档

实际工程：两者结合——用 RAG 缩小候选，再用长上下文做精细对比。
```

## 6. 与其他概念的关系

- **相似概念 vs Token**：Token 是计量单位（"字"的替代品），上下文窗口是"用多少 Token 的容量"。
- **相似概念 vs 工作记忆**：人类心理学中的"工作记忆"约 7±2 项；LLM 的"上下文"是它的工作记忆，但容量按 Token 算而非条目数。
- **相似概念 vs RAG**：RAG 是"用检索给上下文补货"的外部机制，上下文窗口是"内部容量"——两者互补，不互斥。
- **前置概念**：要理解上下文窗口，需要先懂 Transformer、自注意力、Tokenization、位置编码。
- **后续概念**：掌握上下文后，建议继续学习 Prompt Engineering（怎么用满上下文）、Context Engineering（怎么管理上下文中长程状态）、RAG、KV Cache 优化。
- **对比概念**：与"上下文工程（Context Engineering）"的区别——上下文窗口是"容量"问题，上下文工程是"怎么管理内容"的问题。
